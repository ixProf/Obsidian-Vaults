# Chapter 1: Scale From Zero to Millions of Users

## 1. Introduction to System Scalability

### What is Scalability?

الـ Scalability هي قدرة النظام على التعامل مع زيادة الحمل (Load) مع الحفاظ على مستوى مقبول من الأداء والاعتمادية.

لما تبدأ تعمل Application جديد، غالبًا مش بيكون عندك ملايين المستخدمين. ممكن تبدأ بعشرات أو مئات المستخدمين، وبعد كده العدد يزيد تدريجيًا، وده بيؤدي إلى زيادة الضغط على موارد النظام.

الضغط ده ممكن يظهر في صور مختلفة:

- زيادة عدد الـ Requests اللي بتوصل للسيرفر.
- زيادة عدد عمليات القراءة والكتابة على قاعدة البيانات.
- زيادة استهلاك الـ CPU والـ RAM.
- زيادة حجم البيانات المخزنة.
- زيادة زمن الاستجابة (Response Time).
- زيادة احتمالية حدوث Errors أو توقف الخدمة.

علشان كده، الـ Architecture بتاعة النظام مش لازم تكون ثابتة من أول يوم. المفروض تتطور بناءً على احتياجات النظام الفعلية.

### What happens when an application grows?

تخيل إنك عامل E-Commerce Application باستخدام ASP.NET Core وPostgreSQL.

في البداية، عندك عدد قليل من المستخدمين، والسيرفر الواحد قادر يتعامل مع كل الطلبات.

لكن بعد فترة، عدد المستخدمين زاد، وبقى عندك:

- مستخدمون بيستعرضوا المنتجات.
- مستخدمون بيضيفوا منتجات إلى Cart.
- مستخدمون بيعملوا Orders.
- عمليات دفع وتحديث للمخزون.
- عمليات بحث وتقارير.

مع زيادة الحمل، ممكن تكتشف إن السيرفر مش قادر يعالج كل الطلبات بالسرعة المطلوبة، أو إن قاعدة البيانات بقت بطيئة بسبب كثرة الاستعلامات.

هنا بتبدأ تفكر في تطوير الـ Architecture.

الفكرة الأساسية في الشابتر هي إنك تضيف حلولًا تدريجيًا لمعالجة Bottlenecks محددة، بدلًا من بناء نظام معقد من البداية دون حاجة فعلية.

### The scaling journey

الرحلة اللي بيشرحها الشابتر بتمر بالمراحل دي:

1. تشغيل التطبيق على Single Server.
2. فصل Web Tier عن Data Tier.
3. اختيار نوع قاعدة البيانات المناسب.
4. التوسع الرأسي والأفقي.
5. استخدام Load Balancer.
6. استخدام Database Replication.
7. استخدام Cache.
8. استخدام Content Delivery Network (CDN).
9. تحويل Web Tier إلى Stateless Architecture.
10. توزيع النظام على Multiple Data Centers.
11. استخدام Message Queue.
12. إضافة Logging وMetrics وAutomation.
13. توسيع قاعدة البيانات باستخدام Sharding.

كل مرحلة بتحل نوعًا معينًا من المشكلات، ومش شرط كل تطبيق يحتاج إلى جميع المراحل دي.

## 2. Single Server Setup

### What is a Single Server Architecture?

الـ Single Server Architecture هي أبسط صورة ممكنة لتشغيل Application، بحيث تكون المكونات الأساسية موجودة على جهاز واحد.

مثلًا، ممكن يكون عندك:

- Web Server.
- Application Logic.
- Database.
- Cache.

كل المكونات دي بتشتغل على نفس الجهاز.

![[Pasted image 20261025172033.png]]

في المثال ده، المستخدمين بيتعاملوا مع Web Application، والتطبيق بيتواصل مع قاعدة البيانات والـ Cache، وكل ده بيحصل على نفس الجهاز.

### How does a request work?

خلينا نفترض إن المستخدم فتح الموقع وطلب بيانات مستخدم معين.

الخطوات كالتالي:

1. المستخدم يدخل على Domain Name، مثل `api.example.com`.
2. الـ DNS يحوّل اسم النطاق إلى معلومات تساعد على الوصول للسيرفر.
3. الـ Client يرسل HTTP Request.
4. الـ Web Application تستقبل الطلب.
5. التطبيق ينفذ الـ Business Logic المطلوبة.
6. التطبيق يستعلم من قاعدة البيانات لو محتاج بيانات.
7. قاعدة البيانات ترجع النتيجة.
8. التطبيق يحوّل النتيجة إلى HTTP Response.
9. الـ Client يستقبل الاستجابة.

مثال على Request:

```
GET /users/12
```

ومثال على Response:

```
{
  "id": 12,
  "name": "Ahmed"
}
```

الـ Request بيطلب بيانات المستخدم رقم 12، والـ Response بيرجع البيانات المطلوبة في صورة JSON.

### What is DNS?

DNS = Domain Name System

الـ DNS مسؤول عن ترجمة أسماء النطاقات إلى معلومات تساعد الأجهزة في الوصول إلى الوجهة الصحيحة.

بدل ما المستخدم يحتاج يكتب IP Address، يقدر يستخدم اسمًا مفهومًا مثل:

```
www.example.com
```

الـ DNS يساعد الـ Client في معرفة عنوان الوجهة المناسبة للاتصال بها.

### What is HTTP?

HTTP = Hypertext Transfer Protocol

هو البروتوكول المستخدم في التواصل بين الـ Client والـ Server في تطبيقات الويب.

أمثلة على HTTP Methods:

| Method | الاستخدام                                 |
| ------ | ----------------------------------------- |
| GET    | استرجاع البيانات                          |
| POST   | إنشاء مورد جديد أو إرسال بيانات لمعالجتها |
| PUT    | استبدال مورد أو تحديثه وفق تصميم الـ API  |
| PATCH  | تحديث جزء من المورد                       |
| DELETE | حذف مورد                                  |

مثلًا، في ASP.NET Core Web API:

```
GET /api/products
```

ده طلب لجلب المنتجات.

أما:

```
POST /api/orders
```

فده ممكن يستخدم لإنشاء Order جديدة.

### Advantages of a Single Server

التصميم ده مناسب كبداية لعدة أسباب:

- سهل في الإعداد والنشر.
- تكلفته قليلة نسبيًا.
- سهل في المراقبة والصيانة.
- مفيش تعقيد كبير في التواصل بين المكونات.
- مناسب لتجربة فكرة المشروع أو بناء MVP.

### Disadvantages of a Single Server

مع زيادة الحمل، بتظهر مشكلات مهمة.

#### 1. Resource Limitation

كل المكونات بتشارك نفس الموارد.

لو الـ Web Application بتستهلك CPU بكثافة، ده ممكن يؤثر على أداء قاعدة البيانات الموجودة على نفس الجهاز.

كذلك، لو قاعدة البيانات بتستهلك RAM كبيرة، ممكن تقل الذاكرة المتاحة لباقي المكونات.

#### 2. Single Point of Failure

لو الجهاز نفسه تعطل، ممكن كل الخدمات الموجودة عليه تتوقف.

ده مثال على:

SPOF = Single Point of Failure

يعني مكون واحد لو فشل، ممكن يؤدي إلى توقف النظام كله أو وظيفة أساسية منه.

#### 3. Limited Scalability

لما الحمل يزيد، بيكون عندك اختيارات محدودة، خصوصًا لو كل المكونات مرتبطة بجهاز واحد.

ممكن تزود موارد الجهاز، لكن في النهاية هتصل إلى حدود مادية أو اقتصادية.

#### 4. No Independent Scaling

ممكن تكون المشكلة الحقيقية في Database فقط، لكن بما إن التطبيق وقاعدة البيانات على نفس الجهاز، مش هتقدر توسع كل طبقة بصورة مستقلة بنفس السهولة.

الخلاصة: الـ Single Server بداية جيدة، لكنها مش بالضرورة Architecture مناسبة لنظام بيكبر باستمرار.

## 3. Separate Web Tier and Data Tier

لما التطبيق يبدأ يكبر، واحدة من الخطوات الممكنة هي فصل الـ Web Tier عن الـ Data Tier.

### What is the Web Tier?

الـ Web Tier هي الطبقة المسؤولة عن التعامل مع طلبات المستخدمين وتنفيذ منطق التطبيق.

في تطبيق ASP.NET Core، ممكن تشمل:

- استقبال HTTP Requests.
- Authentication وAuthorization.
- Validation.
- تنفيذ Business Logic.
- التواصل مع قاعدة البيانات.
- إنشاء HTTP Responses.

مثلًا، لما المستخدم يطلب إنشاء Order، الـ Web Tier تستقبل الطلب وتتحقق من البيانات والصلاحيات، وبعد كده تنفذ منطق إنشاء الطلب وتتواصل مع قاعدة البيانات.

### What is the Data Tier?

الـ Data Tier مسؤولة عن تخزين البيانات وإدارتها.

ممكن تشمل:

- Relational Database.
- NoSQL Database.
- Database Replicas.
- مكونات تخزين أخرى حسب تصميم النظام.

مثلًا، قاعدة البيانات بتخزن:

- Users.
- Products.
- Orders.
- Payments.
- Inventory.

### Architecture after separation

![[Pasted image 20261025172345.png]]

في التصميم ده، الـ Web Server والـ Database بقوا على أجهزة منفصلة.

### Why do we separate them?

الهدف الأساسي هو Independent Scaling.
يعني كل طبقة نقدر نطورها أو نوسعها حسب احتياجاتها.

#### Example

تخيل إن التطبيق عنده:

- 10,000 مستخدم بيستعرضوا المنتجات.
- عدد أقل من المستخدمين بيعملوا Orders.
- قاعدة البيانات بتتعرض لعدد كبير من عمليات القراءة.

لو المشكلة الأساسية في Web Tier، ممكن نضيف Web Servers.

لكن لو المشكلة الأساسية في Database، ممكن نحتاج تحسين Queries أو زيادة موارد Database Server أو إضافة Replicas.

فصل الطبقات بيساعدنا نعالج المشكلة في مكانها بدلًا من التعامل مع النظام كله كوحدة واحدة.

### Does separation solve every performance problem?

لأ.
فصل الطبقات بيساعد على التوسع المستقل، لكنه مش معناه إن الأداء هيكون ممتاز تلقائيًا.

ممكن تظهر مشكلات جديدة، مثل:

- بطء الشبكة بين Web Server وDatabase.
- استعلامات SQL غير فعالة.
- عدد كبير جدًا من Database Connections.
- ضغط على Database Server.
- استهلاك زائد للموارد في Web Tier.

علشان كده، الفصل خطوة مهمة، لكنه مش حل شامل لكل المشكلات.

## 4. Which Database Should We Use?

اختيار قاعدة البيانات من القرارات المهمة في تصميم النظام، لأن طبيعة البيانات وطريقة الوصول إليها بتؤثر على الأداء والتوسع.

الشابتر بيقارن بين نوعين أساسيين:

1. Relational Databases.
2. Non-Relational Databases.

### 4.1 Relational Databases (SQL / RDBMS)

الـ Relational Database بتخزن البيانات في صورة Tables، وكل Table بتحتوي على Rows وColumns.

أمثلة:

- PostgreSQL.
- MySQL.
- Oracle Database.

#### Example

عندنا جدول للمستخدمين:

Users

| id | name  | email              |
| -- | ----- | ------------------ |
| 1  | Ahmed | ahmed\@example.com |
| 2  | Sara  | sara\@example.com  |

وجدول للطلبات:

Orders

| id  | user_id | total |
| --- | ------- | ----- |
| 101 | 1       | 500   |
| 102 | 2       | 750   |
| 103 | 1       | 300   |

العمود `user_id` بيربط الطلب بالمستخدم صاحب الطلب.

ده مثال على العلاقة بين البيانات.

#### What is a JOIN?

الـ JOIN بتسمح لنا نجيب بيانات من أكثر من جدول في Query واحدة، بناءً على علاقة بينهم.

مثال:

```sql
SELECT Users.name, Orders.total
FROM Users
JOIN Orders
    ON Users.id = Orders.user_id;
```

الاستعلام ده بيربط كل Order بالمستخدم المرتبط بها.

النتيجة هتكون شبيهة بالآتي:

| name  | total |
| ----- | ----- |
| Ahmed | 500   |
| Sara  | 750   |
| Ahmed | 300   |

الـ JOIN مهمة لما نحتاج نربط البيانات الموجودة في جداول مختلفة.

#### When are Relational Databases useful?

بتكون مناسبة في حالات كتير، خصوصًا لما:

- البيانات مترابطة.
- عندنا Schema واضح.
- محتاجين Queries تربط أكثر من جدول.
- محتاجين Transactions للحفاظ على صحة العمليات.
- عندنا عمليات مالية أو Orders أو Inventory.

مثلًا، نظام E-Commerce ممكن يعتمد على PostgreSQL لأن عنده علاقات بين Users وProducts وOrders وPayments.

### 4.2 Non-Relational Databases (NoSQL)

مصطلح NoSQL بيشير إلى مجموعة من قواعد البيانات اللي مش بتعتمد بالضرورة على النموذج العلائقي التقليدي.

أمثلة مذكورة في الشابتر:

- CouchDB.
- Neo4j.
- Cassandra.
- HBase.
- Amazon DynamoDB.

الشابتر بيعرض أربع فئات عامة.

#### A. Key-Value Stores

البيانات بتتخزن في صورة Key وValue.

مثال توضيحي:

```json
"user:101" -> {"name": "Ahmed"}
"user:102" -> {"name": "Sara"}
```

المفتاح بيحدد العنصر اللي عايزين نسترجعه.

النموذج ده مناسب لأنماط وصول تعتمد على البحث باستخدام المفتاح.

#### B. Document Stores

البيانات بتتخزن في صورة Documents، غالبًا ببنية مرنة شبيهة بـ JSON.

مثال:

```json
{
  "id": 101,
  "name": "Ahmed",
  "addresses": [
    {
      "city": "Assiut",
      "type": "home"
    }
  ]
}
```

ممكن Documents مختلفة تحتوي على حقول مختلفة حسب تصميم قاعدة البيانات.

#### C. Column Stores

ده نوع من قواعد البيانات بيستخدم نماذج تخزين وتنظيم تتمحور حول الأعمدة أو مجموعات الأعمدة.

مهم تلاحظ إن المصطلح ده في NoSQL مش بالضرورة نفس معنى Column-Oriented Storage المستخدم في أنظمة تحليل البيانات؛ التفاصيل بتختلف حسب نوع قاعدة البيانات.

#### D. Graph Databases

الـ Graph Databases بتمثل البيانات على هيئة:

- Nodes: الكيانات.
- Edges: العلاقات بين الكيانات.

مثال:

```
Ahmed ---- FRIEND_OF ----> Sara
Sara  ---- WORKS_WITH ---> Ali
```

النموذج ده مفيد لما تكون العلاقات نفسها عنصرًا أساسيًا في الاستعلامات.

### 4.3 When does the chapter suggest NoSQL?

الشابتر بيذكر حالات ممكن تكون فيها NoSQL مناسبة:

- الحاجة إلى Latency منخفضة.
- البيانات غير منظمة أو مش مبنية على علاقات واضحة.
- تخزين واسترجاع بيانات متسلسلة مثل JSON أو XML أو YAML.
- التعامل مع كميات ضخمة من البيانات.

لكن لازم نفهم إن دي اعتبارات عامة، مش قواعد مطلقة.

مش معنى إن عندك ملايين المستخدمين إنك لازم تستخدم NoSQL، ومش معنى إنك بتستخدم SQL إن النظام مش هيقدر يتوسع.

القرار بيتحدد حسب:

- طبيعة البيانات.
- أنماط الاستعلامات.
- متطلبات الاتساق.
- حجم عمليات القراءة والكتابة.
- متطلبات التوسع.
- قدرات قاعدة البيانات نفسها.

### SQL vs. NoSQL

| المقارنة       | SQL / Relational                 | NoSQL                            |
| -------------- | -------------------------------- | -------------------------------- |
| نموذج البيانات | Tables مترابطة                   | يختلف حسب النوع                  |
| Schema         | غالبًا محدد وواضح                | قد يكون أكثر مرونة               |
| JOIN           | مدعومة في النموذج العلائقي       | تختلف الإمكانيات حسب النظام      |
| الاستخدام      | بيانات مترابطة وTransactions     | نماذج وصول وبيانات متنوعة        |
| التوسع         | رأسي أو أفقي حسب النظام والتصميم | أفقي في أنظمة كثيرة، حسب التصميم |
| الاختيار       | حسب متطلبات المشروع              | حسب متطلبات المشروع              |

الفكرة الأساسية: اختار قاعدة البيانات بناءً على احتياجات التطبيق، مش بناءً على شهرة التقنية.

## 5. Vertical Scaling vs. Horizontal Scaling

دي من أهم النقاط في الشابتر.

فيه طريقتان أساسيتان لزيادة قدرة النظام على التعامل مع الحمل:

1. Vertical Scaling.
2. Horizontal Scaling.

### 5.1 Vertical Scaling (Scale Up)

الـ Vertical Scaling معناها إنك تزود موارد الجهاز الحالي.

مثلًا:

- زيادة CPU Cores.
- زيادة RAM.
- استخدام Storage أسرع.
- استخدام جهاز أقوى.

#### Example

عندك Web Server بمواصفات:

```
CPU: 2 Cores
RAM: 4 GB
```

لما الحمل يزيد، تنقله إلى جهاز بمواصفات:

```
CPU: 8 Cores
RAM: 16 GB
```

أنت هنا زودت قدرة الجهاز نفسه بدلًا من إضافة أجهزة أخرى.

#### Advantages

- أسهل نسبيًا في الإدارة.
- مش محتاج بالضرورة توزع الطلبات على Servers متعددة.
- ممكن يكون حلًا سريعًا لما الموارد الحالية مش كافية.

#### Disadvantages

- كل جهاز له حدود قصوى.
- الأجهزة الأقوى ممكن تكون مكلفة.
- لو التطبيق معتمد على جهاز واحد، تعطل الجهاز قد يؤثر على الخدمة بالكامل.
- مش كل التطبيقات بتستفيد من زيادة الموارد بنفس النسبة.

### 5.2 Horizontal Scaling (Scale Out)

الـ Horizontal Scaling معناها إنك تضيف Servers جديدة بدلًا من الاعتماد على تقوية Server واحد فقط.

#### Example

بدلًا من Web Server واحد قوي، يبقى عندك ثلاثة Web Servers:

![[Pasted image 20261025173007.png]]
لكن في التطبيق الفعلي، غالبًا هنحتاج Component يوزع الطلبات بينهم، وهو الـ Load Balancer.

![[Pasted image 20261025173027.png]]
#### Advantages

- نقدر نضيف Servers عند زيادة الحمل.
- ممكن نقلل تأثير تعطل Server واحد لو فيه Servers سليمة بديلة.
- نقدر نوزع الحمل على أجهزة متعددة.
- مناسب للأنظمة اللي محتاجة توسع تدريجي.

#### Disadvantages

- محتاجين إدارة توزيع الطلبات.
- لازم نفكر في تخزين Session State.
- لازم نتعامل مع الأعطال بين الأجهزة.
- التواصل عبر الشبكة بيضيف تعقيدًا.
- بعض العمليات قد تحتاج تنسيقًا بين أكثر من Server.

### Comparison

| النقطة       | Vertical Scaling           | Horizontal Scaling            |
| ------------ | -------------------------- | ----------------------------- |
| الطريقة      | تقوية الجهاز الحالي        | إضافة أجهزة                   |
| التعقيد      | أقل غالبًا                 | أعلى غالبًا                   |
| حدود التوسع  | حدود الجهاز                | إضافة أجهزة أخرى ممكنة        |
| توزيع الحمل  | مش ضروري                   | غالبًا مطلوب                  |
| تحمل الأعطال | يعتمد على التصميم          | يمكن تحسينه بتعدد الأجهزة     |
| التكلفة      | قد ترتفع مع الأجهزة القوية | تتغير حسب عدد الأجهزة والبنية |

ملاحظة مهمة: الـ Horizontal Scaling مش ضمان تلقائي للـ High Availability. لازم يكون النظام مصممًا للتعامل مع الأعطال، ولازم نتجنب وجود نقطة فشل وحيدة في المكونات المهمة.

## 6. Load Balancer

### 6.1 What is a Load Balancer?

الـ Load Balancer هو Component بيستقبل الطلبات ويوزعها على مجموعة من Servers.

المشكلة اللي بيعالجها هي إن Server واحد ممكن يوصل إلى حدوده، سواء من ناحية عدد الطلبات أو استهلاك الموارد.

بدلًا من توجيه كل المستخدمين إلى Server واحد، بنوزع الطلبات على عدة Servers.

### 6.2 Architecture

![[Pasted image 20261025173036.png]]

المستخدم بيتصل بالـ Load Balancer، والـ Load Balancer يوجه الطلب إلى Web Server مناسب.

### 6.3 How does it improve scalability?

تخيل إن عندك Server واحد يقدر يتعامل مع حمل معين.

لما عدد المستخدمين يزيد، ممكن تضيف Server آخر، وبعدها تضيفه إلى مجموعة الـ Servers اللي الـ Load Balancer بيوزع عليها الطلبات.

ده بيسمح بتوسيع Web Tier أفقيًا.

### 6.4 What happens when a server fails?

لو Server 1 تعطل، ممكن الـ Load Balancer يوجه الطلبات إلى Server 2.

لكن علشان ده يحصل بشكل صحيح، لازم النظام يكتشف إن Server 1 غير سليم.

هنا بيظهر مفهوم:

Health Checks

وهي فحوصات بتساعد على معرفة هل الـ Server قادر على استقبال الطلبات وتنفيذها بشكل طبيعي أم لا.

لو Server فشل في Health Check، ممكن يتم استبعاده مؤقتًا من مجموعة الـ Servers المستخدمة.

### 6.5 Public IP and Private IP

#### Public IP

عنوان يمكن الوصول إليه من الإنترنت، وفق إعدادات الشبكة والجدار الناري.

#### Private IP

عنوان يستخدم داخل شبكة خاصة، ويُستخدم عادةً للتواصل الداخلي بين مكونات النظام.

في التصميم اللي بيعرضه الشابتر:

- المستخدمون بيتصلوا بالـ Public IP الخاص بالـ Load Balancer.
- الـ Load Balancer يتواصل مع Web Servers عبر الشبكة الداخلية.
- الـ Web Servers مش لازم تكون مكشوفة مباشرة للإنترنت.

ده بيساعد في تقليل سطح التعرض المباشر، لكنه لا يغني عن Security Controls المناسبة.

### 6.6 Does a Load Balancer solve every problem?

لأ.

#### Database Bottleneck

لو كل Web Servers بتعتمد على Database بطيئة، فالـ Load Balancer مش هيحل بطء قاعدة البيانات.

#### Stateful Sessions

لو Session Data موجودة داخل Server معين، ممكن الطلب التالي يروح إلى Server آخر وميلقاش بيانات الجلسة.

#### Load Balancer Failure

لو عندك Load Balancer وحيد وتعطل، ممكن الطلبات كلها تتأثر.

#### Shared Dependencies

لو كل Web Servers بتعتمد على خدمة مشتركة متعطلة، تعدد الـ Web Servers مش هيحل المشكلة.

الخلاصة: الـ Load Balancer بيساعد على توزيع الطلبات، لكنه مش بديل عن تصميم النظام لتحمل الأعطال ومراقبة جميع المكونات المهمة.

## 7. Database Replication

### 7.1 What is Database Replication?

الـ Database Replication هي الاحتفاظ بنسخ من البيانات على أكثر من Database Server.

الشابتر بيشرح نموذجًا فيه:

- Master.
- Slaves أو Replicas.

في النموذج ده، الـ Master بتستقبل عمليات الكتابة، والـ Replicas بتحتفظ بنسخ من البيانات، وغالبًا تُستخدم لتوزيع عمليات القراءة.

> أسماء الأدوار وآليات الكتابة والقراءة بتختلف بين أنظمة قواعد البيانات، لكن النموذج ده هو المستخدم في شرح الشابتر.

### 7.2 Architecture

![[Pasted image 20261025173335.png]]
### 7.3 Why do we need replication?

#### A. Performance

لو عندك عدد كبير من عمليات القراءة، ممكن توزعها على Replicas بدلًا من تحميلها كلها على Master.

مثال:

تطبيق فيه آلاف المستخدمين بيستعرضوا المنتجات، بينما عدد عمليات تعديل المنتجات أقل.

ممكن توجيه بعض قراءات المنتجات إلى Replicas، مع توجيه عمليات التعديل إلى قاعدة البيانات الأساسية.

ده يساعد على توزيع حمل القراءة.

#### B. Reliability

وجود نسخ متعددة من البيانات ممكن يقلل خطر فقدان الوصول إلى البيانات بسبب تعطل جهاز واحد، بشرط وجود نسخ سليمة وإمكانية الوصول إليها.

#### C. High Availability

لو Replica تعطلت، ممكن توجيه عمليات القراءة إلى Replica أخرى.

أما لو Master تعطلت، فقد يحتاج النظام إلى ترقية Replica أخرى لتصبح قاعدة البيانات الأساسية.

الخطوة دي بتحتاج آلية Failover مناسبة.

### 7.4 What happens if a Slave fails?

لو Replica تعطلت:

1. النظام يكتشف العطل.
2. يوقف توجيه القراءات إليها.
3. يوجه القراءات إلى Replicas أخرى سليمة أو إلى Master وفق التصميم.
4. يتم إصلاحها أو إنشاء Replica بديلة.
5. تتم مزامنتها مع مصدر البيانات.

التفاصيل الفعلية بتعتمد على نظام قاعدة البيانات وإعداداته.

### 7.5 What happens if the Master fails?

لو Master تعطلت، النظام ممكن يحتاج إلى:

1. اكتشاف العطل.
2. اختيار Replica مناسبة.
3. ترقيتها إلى Primary أو Master.
4. توجيه عمليات الكتابة إليها.
5. إعادة بناء النسخة القديمة أو مزامنتها بعد استعادة الخدمة.

المشكلة إن Replica ممكن تكون متأخرة عن آخر التحديثات اللي وصلت إلى Master.

علشان كده، لازم نراعي احتمالية فقدان بعض التحديثات الأخيرة أو الحاجة إلى استعادتها.

### 7.6 Replication Lag

الـ Replication Lag هو التأخير بين حدوث التغيير في المصدر ووصوله إلى Replica.

مثال:

1. المستخدم يغير عنوانه.
2. التعديل يتم على Master.
3. التطبيق يرسل طلب قراءة جديدًا.
4. الطلب يذهب إلى Replica لم يصلها التعديل بعد.
5. المستخدم يشوف العنوان القديم مؤقتًا.

المشكلة دي مهمة جدًا في التطبيقات اللي بتحتاج قراءة أحدث البيانات مباشرة بعد الكتابة.

### 7.7 Replication vs. Backup

الـ Replication مش بديل كامل عن Backup.

لو مستخدم حذف بيانات مهمة بالخطأ، ممكن الحذف ينتقل إلى Replicas أيضًا.

أما الـ Backup فهدفها توفير نسخة يمكن استخدامها لاستعادة البيانات بعد بعض أنواع الأعطال أو الأخطاء.

## 8. Cache


### 8.1 What is Caching?

الـ Cache هي مساحة تخزين مؤقت بنحتفظ فيها ببيانات أو نتائج متكررة الاستخدام، علشان نقدر نوصل إليها بسرعة بدلًا من إعادة تنفيذ نفس العمليات كل مرة.

مثال:

عندك E-Commerce Application، وصفحة المنتجات بتستعلم عن بيانات معينة بشكل متكرر.

لو كل طلب بيعيد نفس الاستعلامات على قاعدة البيانات، ده ممكن يستهلك موارد كبيرة.

ممكن نخزن بعض النتائج في Cache، بحيث الطلبات التالية تحصل عليها بسرعة.

### 8.2 Why do we need Cache?

- تقليل زمن الاستجابة.
- تقليل عدد الاستعلامات على قاعدة البيانات.
- تقليل الضغط على Database.
- تحسين قدرة النظام على التعامل مع الطلبات المتكررة.

### 8.3 How does Cache work?


![[Pasted image 20261025173636.png]]

### 8.4 Cache Hit

الـ Cache Hit معناها إن البيانات المطلوبة موجودة في Cache وصالحة للاستخدام.

في الحالة دي، التطبيق يقدر يرجع البيانات من Cache بدلًا من الاستعلام من قاعدة البيانات.

### 8.5 Cache Miss

الـ Cache Miss معناها إن البيانات المطلوبة مش موجودة في Cache، أو انتهت صلاحيتها، أو تم حذفها.

في المثال اللي بيشرحه الشابتر:

1. التطبيق يبحث عن البيانات في Cache.
2. لا يجدها.
3. يستعلم من Database.
4. يخزن النتيجة في Cache.
5. يرجع البيانات إلى المستخدم.

الأسلوب ده قريب من فكرة Read-through Caching، مع ملاحظة إن التطبيق نفسه قد ينفذ الخطوات دي حسب طريقة تصميم الـ Cache Layer.

### 8.6 What data should we cache?

الـ Cache بتكون مفيدة بشكل خاص للبيانات اللي:

- بيتكرر طلبها كثيرًا.
- تكلفة الحصول عليها مرتفعة نسبيًا.
- لا تتغير باستمرار، أو يمكن قبول تأخر ظهور التعديلات عليها لفترة محددة.

أمثلة:

- بيانات المنتجات.
- إعدادات التطبيق.
- نتائج بعض الاستعلامات المتكررة.
- بيانات عامة بيطلبها عدد كبير من المستخدمين.

أما البيانات اللي لازم تكون محدثة لحظيًا، فمحتاجة تصميمًا أكثر حذرًا.

### 8.7 TTL (Time To Live)

الـ TTL هي المدة اللي تفضل فيها البيانات داخل Cache قبل اعتبارها منتهية الصلاحية.

مثال:

لو خزنت بيانات منتج لمدة 5 دقائق، فممكن تستخدم النسخة المخزنة خلال المدة دي، وبعد انتهاء المدة تحتاج إلى إعادة جلب البيانات وفق سياسة الـ Cache.

#### Short TTL

لو مدة الصلاحية قصيرة جدًا:

- البيانات بتتجدد كثيرًا.
- الاستعلامات على Database بتزيد.
- فائدة Cache ممكن تقل.

#### Long TTL

لو مدة الصلاحية طويلة جدًا:

- ممكن تفضل البيانات القديمة موجودة لفترة طويلة.
- التعديلات الجديدة ممكن ما تظهرش فورًا للمستخدمين.

اختيار TTL بيعتمد على طبيعة البيانات ومتطلبات حداثتها.

### 8.8 Cache Consistency

دي من أهم التحديات في استخدام Cache.

المشكلة هي ضمان إن البيانات الموجودة في Cache متوافقة مع البيانات الأساسية.

مثال:

1. سعر المنتج في Database يساوي 100.
2. التطبيق يخزن السعر في Cache.
3. السعر يتغير في Database إلى 120.
4. Cache ما زالت تحتوي على السعر القديم.
5. المستخدم يحصل على السعر 100.

علشان تقلل المشكلة دي، ممكن تستخدم سياسات مثل:

- حذف Cache Entry عند تعديل البيانات.
- تحديث Cache بعد تعديل البيانات.
- تحديد TTL مناسبة.
- استخدام آليات لإبطال البيانات القديمة.

لكن مفيش سياسة واحدة مناسبة لكل الأنظمة، وبعض الحلول بتحتاج مراعاة حالات الفشل بين تحديث Database وتحديث Cache.

### 8.9 Cache Eviction Policies

الـ Cache لها حجم محدود. لما تمتلئ، ممكن تحتاج إلى إزالة بعض العناصر لإفساح مساحة.

العملية دي اسمها Eviction.

#### LRU: Least Recently Used

إزالة العنصر الأقل استخدامًا في الفترة الأخيرة.

الفكرة إن العنصر اللي لم يتم الوصول إليه منذ وقت طويل قد يكون أقل أهمية من العناصر المستخدمة حديثًا.

#### LFU: Least Frequently Used

إزالة العنصر الأقل تكرارًا في الاستخدام.

الفكرة هنا هي عدد مرات الوصول إلى العنصر، مش فقط آخر مرة تم استخدامه فيها.

#### FIFO: First In, First Out

إزالة العنصر الذي دخل Cache أولًا.

| Policy | تعتمد على       |
| ------ | --------------- |
| LRU    | حداثة الاستخدام |
| LFU    | تكرار الاستخدام |
| FIFO   | ترتيب الدخول    |

كل سياسة لها مزايا وعيوب، والاختيار بيعتمد على نمط استخدام البيانات.

### 8.10 Cache as a Single Point of Failure

لو التطبيق معتمد على Cache Server واحدة، وتعطلت، ممكن تظهر مشكلات.

في بعض الأنظمة، التطبيق يقدر يرجع إلى Database مباشرة، لكن ده ممكن يسبب ضغطًا مفاجئًا عليها.

وفي أنظمة أخرى، بعض الوظائف قد لا تستطيع العمل بصورة طبيعية دون Cache.

علشان كده، لازم نحدد سلوك النظام عند تعطل Cache، ونراعي توفر الموارد والنسخ البديلة عند الحاجة.

## 9. Content Delivery Network (CDN)

### 9.1 What is a CDN?

الـ Content Delivery Network هي شبكة من Servers موزعة جغرافيًا، هدفها تقديم المحتوى للمستخدمين من مواقع مناسبة جغرافيًا بدلًا من الاعتماد دائمًا على Server مركزي بعيد.

الشابتر بيركز خصوصًا على Static Content.

### 9.2 What is Static Content?

هو المحتوى اللي يمكن تقديمه كملفات دون الحاجة إلى توليده من جديد بناءً على كل Request.

أمثلة:

- Images.
- CSS Files.
- JavaScript Files.
- Videos.

### 9.3 Why do we need CDN?

تخيل إن الـ Origin Server موجود في الولايات المتحدة، وفيه مستخدم في مصر بيطلب صورة.

لو كل طلب للصورة لازم يسافر إلى السيرفر البعيد، ممكن المسافة الشبكية تزيد زمن الاستجابة.

الـ CDN بتساعد في تخزين نسخة من المحتوى على Server أقرب للمستخدم.

بالتالي، الطلبات التالية ممكن تحصل على الملف من موقع أقرب جغرافيًا.

### 9.4 How does CDN work?

![[Pasted image 20261025173819.png]]

الـ Origin هو المصدر الأساسي للملف، وممكن يكون Web Server أو Object Storage.

لو الملف موجود في CDN Cache، يتم إرجاعه مباشرة.

لو الملف غير موجود، ممكن الـ CDN تجلبه من Origin ثم تحتفظ بنسخة منه وفق إعدادات التخزين المؤقت.

### 9.5 CDN Hit and CDN Miss

- CDN Hit: المحتوى المطلوب موجود في Cache الخاصة بالـ CDN.
- CDN Miss: المحتوى يحتاج إلى الجلب من Origin.

الـ CDN بتقلل الطلبات المتكررة على Origin لما يكون المحتوى قابلًا للتخزين المؤقت.

### 9.6 TTL and Cache Invalidation

مثل أي Cache، لازم نحدد مدة صلاحية المحتوى.

لو الملف اتغير، لكن CDN ما زالت تقدم النسخة القديمة، المستخدم ممكن يشوف محتوى غير محدث.

فيه أكثر من طريقة للتعامل مع المشكلة:

- ضبط TTL.
- استخدام Cache Invalidation لإزالة النسخة القديمة.
- استخدام Versioning في أسماء الملفات.

مثال:

```
/styles.css?v=1
/styles.css?v=2
```

لما يتغير الملف، ممكن يتغير الإصدار المستخدم في الرابط، وبالتالي يتعامل النظام مع الرابط الجديد كملف مختلف.

### 9.7 CDN Costs

استخدام CDN قد يضيف تكاليف، مثل تكاليف نقل البيانات أو التخزين أو عدد الطلبات، حسب مزود الخدمة.

علشان كده، لازم نراعي طبيعة المحتوى وحجم استخدامه، ونختار الإعدادات المناسبة.

### 9.8 Cache vs. CDN

| المقارنة | Application Cache                 | CDN                                         |
| -------- | --------------------------------- | ------------------------------------------- |
| الهدف    | تقليل العمل المتكرر               | تقديم المحتوى بكفاءة جغرافية                |
| المحتوى  | بيانات أو نتائج متكررة            | غالبًا ملفات Static Content في سياق الشابتر |
| الموقع   | قريب من Application أو داخل بنيته | موزع جغرافيًا                               |
| مثال     | بيانات منتج مخزنة مؤقتًا          | صورة منتج مخزنة على CDN                     |

الـ CDN نفسها بتستخدم Caching؛ الفرق الأساسي هو دورها ومكانها ونوع المحتوى اللي بتخدمه.

## 10. Stateless Web Tier

### 10.1 What is State?

الـ State هي المعلومات اللي بتعبّر عن حالة معينة في النظام أو عن تفاعلات المستخدم.

مثال مهم في الشابتر هو Session Data.

تخيل إن المستخدم سجل الدخول، والتطبيق بيحتاج يحتفظ بمعلومات عن الجلسة علشان يتعامل مع الطلبات التالية.

السؤال هنا: المعلومات دي متخزنة فين؟

الإجابة هي اللي بتفرق بين Stateful وStateless Architecture.

### 10.2 Stateful Architecture

في Stateful Architecture، ممكن يحتفظ كل Web Server ببيانات الجلسات الموجودة عليه.

مثال:

![[Pasted image 20261025174023.png]]

لو المستخدم A أرسل طلبًا جديدًا، لكنه وصل إلى Server 2 بدلًا من Server 1، ممكن Server 2 ما يلاقيش Session A.

المشكلة دي بتظهر لما نستخدم عدة Web Servers ونوزع الطلبات بينهم.

### 10.3 Sticky Sessions

من الحلول الممكنة استخدام Sticky Sessions.

الفكرة إن الـ Load Balancer يحاول توجيه طلبات المستخدم نفسه إلى نفس Web Server.

مثال:

```
User A ---> Server 1
User A ---> Server 1
User A ---> Server 1
```

لكن الحل ده له عيوب:

- يقلل مرونة توزيع الطلبات.
- ممكن يسبب عدم توازن الحمل.
- تعطل Server قد يؤثر على المستخدمين المرتبطين به.
- إضافة أو إزالة Servers قد تصبح أكثر تعقيدًا.

### 10.4 Stateless Architecture

في Stateless Architecture، الـ Web Server لا يعتمد على الاحتفاظ بحالة المستخدم محليًا بين الطلبات.

بدلًا من ذلك، يتم تخزين الحالة المطلوبة في Shared Store يمكن لجميع Web Servers الوصول إليه.

أمثلة على Shared Store:

- Relational Database.
- NoSQL Database.
- Redis.
- Memcached.

### 10.6 Why is Stateless Architecture useful?

### 10.7 Does Stateless mean the application has no state?

البيانات نفسها ما زالت موجودة في Database أو Shared Store.

## 11. Multiple Data Centers

### 11.1 What is a Data Center?

الـ Data Center هي بنية تحتية تحتوي على Servers وNetworking وStorage ومكونات أخرى لتشغيل الأنظمة.

في الأنظمة الكبيرة، ممكن نشغل التطبيق في أكثر من Data Center.

### 11.2 Why use multiple Data Centers?

هناك سببان مهمان في سياق الشابتر:

- تحسين التعامل مع الأعطال على مستوى مركز كامل.
- تقليل زمن الاستجابة لبعض المستخدمين عن طريق تقريب الخدمة منهم جغرافيًا.

مثلًا، ممكن يكون عندك مركز في الولايات المتحدة وآخر في أوروبا.

بدلًا من الاعتماد على مركز واحد لكل المستخدمين، ممكن توجيه المستخدمين إلى مركز مناسب.

### 11.3 GeoDNS

الـ GeoDNS ممكن تساعد في توجيه المستخدمين إلى Data Center مناسب اعتمادًا على موقعهم الجغرافي أو سياسات التوجيه.

#### Failover

#### Testing and Deployment

## 12. Message Queue

### 12.1 Why do we need Message Queues?

بعض المهام بتحتاج وقتًا طويلًا للتنفيذ.

لو Web Server نفذ كل المهمة داخل HTTP Request، المستخدم ممكن يضطر ينتظر وقتًا طويلًا، والسيرفر يفضل مشغولًا بالعملية.

الشابتر بيستخدم مثال معالجة الصور.

تخيل إن المستخدم رفع صورة، والتطبيق محتاج ينفذ عليها عمليات مثل:

- تغيير الحجم.
- القص.
- تحسين الوضوح.
- إضافة تأثيرات.
- حفظ النسخة النهائية.

لو كل العمليات دي اتنفذت قبل إرجاع HTTP Response، الطلب ممكن يستغرق وقتًا طويلًا.

### 12.2 What is a Message Queue?

الـ Message Queue هي وسيط لتخزين الرسائل أو المهام مؤقتًا، بحيث يقدر Component يرسل مهمة، وComponent آخر يعالجها لاحقًا.

المكونات الأساسية:

- Producer.
- Queue.
- Consumer.

### 12.3 Producer

الـ Producer هو المكون اللي بينشئ الرسالة أو المهمة ويرسلها إلى Queue.

في مثال معالجة الصور، ممكن يكون Web Application هي الـ Producer.

### 12.4 Queue

الـ Queue تحتفظ بالرسائل في انتظار معالجتها.

ده بيساعد على فصل وقت إرسال المهمة عن وقت تنفيذها.

### 12.5 Consumer

الـ Consumer هو المكون اللي ==يستقبل الرسائل وينفذ المهام المطلوبة==.

ممكن يكون Background Worker مسؤولًا عن معالجة الصور.

### 12.7 Processing an Image Without a Queue

من غير Queue:

1. المستخدم يرفع الصورة.
2. Web Application تبدأ معالجة الصورة.
3. السيرفر يفضل مشغولًا حتى تنتهي المهمة.
4. المستخدم ينتظر HTTP Response.
5. السيرفر يرجع النتيجة.

المشكلة إن المهمة الطويلة بتفضل مرتبطة بمسار الطلب المباشر.

### 12.8 Processing an Image With a Queue

باستخدام Queue:

1. المستخدم يرسل طلب المعالجة.
2. Web Application تنشئ Job.
3. التطبيق يرسل Job إلى Queue.
4. التطبيق يرجع Response يفيد بقبول المهمة.
5. Background Worker يستقبل المهمة.
6. Worker يعالج الصورة.
7. النتيجة تُحفظ أو يتم إخطار المستخدم باكتمال المهمة.

الاستجابة المبكرة هنا لا تعني إن المعالجة انتهت؛ هي تعني إن النظام قبل المهمة.

### 12.9 Decoupling

الـ Decoupling يعني تقليل الاعتماد المباشر بين المكونات.

من غير Queue، ممكن يكون Web Application مضطرة تنتظر انتهاء تنفيذ عملية طويلة.

لكن ==باستخدام Queue، التطبيق يقدر يرسل المهمة دون انتظار تنفيذها بالكامل==.

كذلك، لو الـ Consumer غير متاح مؤقتًا، ممكن الرسائل تفضل محفوظة حتى يعود، حسب إعدادات Queue.

### 12.10 Independent Scaling

ممكن توسع Web Tier وWorker Tier بصورة مستقلة.

مثلًا:

- تزود Web Servers لاستقبال Requests أكثر.
- تزود Workers لمعالجة عدد أكبر من المهام.
- تراقب حجم Queue لتعرف هل المهام بتتراكم.

لو المهام بتوصل أسرع من قدرة Workers على معالجتها، حجم Queue ممكن يزيد باستمرار.

### 12.11 Does a Queue make tasks faster?

مش بالضرورة.

الـ Queue مش بتلغي وقت تنفيذ المهمة، لكنها بتفصل تنفيذها عن الطلب المباشر.

وده ممكن يحسن استجابة الـ API، ويساعد على تنظيم الحمل، لكنه لا يعني إن النتيجة النهائية هتكون جاهزة في وقت أقل دائمًا.

كمان لازم نفكر في:

- فشل الرسائل.
- إعادة المحاولة.
- الرسائل اللي لا يمكن معالجتها.
- احتمال تنفيذ نفس المهمة أكثر من مرة.
- كيفية معرفة المستخدم إن المهمة اكتملت.

## 13. Logging, Metrics, and Automation

لما النظام يتكون من Servers وDatabase وCache وWorkers ومراكز بيانات متعددة، معرفة المشكلة بتصبح أصعب.

علشان كده، الشابتر بيتكلم عن أهمية مراقبة النظام وأتمتة بعض العمليات.

### 13.1 Logging

الـ Logging هو تسجيل الأحداث والتفاصيل اللي بتحصل داخل التطبيق والبنية التحتية.

أمثلة:

- Exceptions.
- فشل بعض Requests.
- أحداث تشغيل Background Jobs.
- أخطاء الاتصال بقاعدة البيانات.

#### Centralized Logging

في النظام الموزع، كل Server ممكن يكون عنده Logs خاصة به.

بدلًا من الدخول إلى كل Server بصورة منفصلة، ممكن نجمع الـ Logs في نظام مركزي.

ده بيساعد على:

- البحث عن الأخطاء.
- تتبع الأحداث.
- فهم تسلسل المشكلة.
- مقارنة الأحداث بين مكونات مختلفة.

### 13.2 Metrics

الـ Metrics هي ==قياسات رقمية تساعدنا على فهم أداء النظام وحالته.==

الشابتر بيذكر ثلاثة مستويات.

#### A. Host-level Metrics

قياسات مرتبطة بجهاز معين، مثل:

- CPU Utilization.
- Memory Usage.
- Disk I/O.

مثلًا، ارتفاع استهلاك CPU بصورة مستمرة ممكن يكون علامة على ضغط زائد أو عملية مكلفة.

#### B. Aggregated-level Metrics

قياسات مجمعة على مستوى طبقة كاملة.

مثلًا، بدلًا من النظر إلى Web Server واحد، نراقب أداء Web Tier كلها.

ممكن نتابع مؤشرات مثل:

- متوسط Response Time.
- عدد Requests.
- معدلات الأخطاء.
- استهلاك الموارد على مستوى مجموعة Servers.

#### C. Business Metrics

قياسات مرتبطة بنجاح المنتج أو العمل نفسه.

أمثلة:

- Daily Active Users.
- Retention.
- Revenue.

الـ Business Metrics مهمة لأن النظام ممكن يكون سريعًا تقنيًا، لكن ده مش بالضرورة معناه إن المنتج بيحقق أهدافه.

### 13.3 Logging vs. Metrics

| المقارنة     | Logging          | Metrics                  |
| ------------ | ---------------- | ------------------------ |
| نوع البيانات | أحداث وتفاصيل    | قياسات رقمية             |
| الهدف        | فهم ما حدث       | متابعة الأداء والاتجاهات |
| مثال         | تفاصيل Exception | ارتفاع نسبة الأخطاء      |
| الاستخدام    | التحقيق في مشكلة | اكتشاف تغير أو مشكلة     |

غالبًا بنحتاج الاثنين معًا.

مثلًا، Metrics ممكن توضح إن Response Time ارتفع، وبعد كده نراجع Logs علشان نفهم سبب المشكلة.

### 13.4 Automation

الـ Automation هي استخدام أدوات لتنفيذ مهام متكررة تلقائيًا بدلًا من تنفيذها يدويًا في كل مرة.

أمثلة:

- Build.
- Automated Tests.
- Deployment.

الأتمتة بتساعد على تقليل الأخطاء اليدوية وتوحيد خطوات التنفيذ.

### 13.5 Continuous Integration (CI)

الـ Continuous Integration هي ممارسة دمج تغييرات الكود والتحقق منها بصورة مستمرة باستخدام عمليات آلية.

مثلًا، عند إرسال تغييرات جديدة إلى Repository:

1. يتم تشغيل Build.
2. يتم تشغيل Automated Tests.
3. تظهر نتائج التحقق.
4. يقدر الفريق يكتشف المشكلات مبكرًا.

الـ CI جزء من الممارسات اللي بتساعد على الحفاظ على جودة النظام مع استمرار التطوير.

## 14. Database Scaling

حتى لو عندك Web Tier قوية، ممكن قاعدة البيانات تكون هي عنق الزجاجة.

مثلًا:

- الاستعلامات بتستغرق وقتًا طويلًا.
- عدد عمليات القراءة والكتابة كبير.
- حجم البيانات بيزيد.
- الموارد المتاحة لقاعدة البيانات غير كافية.

الشابتر بيعرض اتجاهين أساسيين للتوسع.

### 14.1 Vertical Scaling for Databases

يعني زيادة موارد Database Server نفسها.

مثلًا:

- زيادة RAM.
- زيادة CPU.
- استخدام Storage أسرع.

#### Advantages

- بسيط نسبيًا مقارنة ببعض تصميمات التوزيع.
- ممكن يحسن الأداء عند وجود موارد غير كافية.

#### Disadvantages

- الجهاز له حدود.
- زيادة الموارد ممكن تكون مكلفة.
- الاعتماد على Database Server واحدة قد يجعلها نقطة فشل مهمة.

### 14.2 Horizontal Scaling: Sharding

==الـ Sharding هو تقسيم البيانات إلى أجزاء وتوزيعها على Database Servers متعددة.==

كل جزء يسمى Shard.

بدلًا من الاحتفاظ بكل البيانات على Server واحدة، يتم توزيعها حسب قاعدة معينة.

### 14.3 How does Sharding work?

تخيل عندك تطبيق يحتوي على بيانات ملايين المستخدمين.

بدلًا من تخزين كل المستخدمين في Database واحدة، ممكن تقسيمهم إلى Shards.

مثلًا:

### 14.4 Sharding Key

الـ Sharding Key أو Partition Key هو الحقل أو مجموعة الحقول المستخدمة لتحديد مكان تخزين البيانات.

اختيار المفتاح مهم جدًا، لأنه بيؤثر على:

- توزيع البيانات.
- توزيع الحمل.
- سهولة الوصول إلى البيانات.
- احتمالية ظهور Hotspots.
- تكلفة نقل البيانات مستقبلًا.

لو اخترنا مفتاحًا غير مناسب، ممكن بعض Shards تحمل بيانات أكثر أو تستقبل Requests أكثر من غيرها.

### 14.5 Hash Function Example

الشابتر بيعرض المثال التالي:

```
shard_id = user_id % 4
```

الرمز `%` هو Modulo Operator، وبيحسب باقي القسمة.

بالتالي:

| user_id | الحساب  | shard_id |
| ------- | ------- | -------- |
| 100     | 100 % 4 | 0        |
| 101     | 101 % 4 | 1        |
| 102     | 102 % 4 | 2        |
| 103     | 103 % 4 | 3        |
| 104     | 104 % 4 | 0        |

لو عندك أربع Shards، نتيجة باقي القسمة بتحدد الـ Shard المستهدفة في المثال ده.

### 14.6 What is Resharding?

الـ Resharding هو إعادة توزيع البيانات بين Shards.

ممكن نحتاج إليه لما:

- حجم البيانات يزيد.
- بعض Shards تصبح أكبر بكثير من غيرها.
- الحمل يتوزع بصورة غير متوازنة.
- نحتاج إلى تغيير عدد Shards أو استراتيجية التوزيع.

المشكلة إن نقل البيانات وتغيير قواعد التوجيه ممكن يكون معقدًا.

الشابتر بيذكر Consistent Hashing باعتبارها إحدى التقنيات اللي بتساعد في تقليل حجم إعادة التوزيع في بعض تصميمات الأنظمة الموزعة.

### 14.7 Hotspot Key and Celebrity Problem

ممكن توزيع البيانات يكون متوازنًا من حيث الحجم، لكن الحمل نفسه يفضل غير متوازن.

مثال:

تطبيق Social Media فيه بيانات مستخدم مشهور جدًا، وملايين الأشخاص بيطلبوا بياناته.

لو كل الطلبات دي بتروح إلى Shard واحدة، ممكن تصبح هذه الـ Shard نقطة ضغط، حتى لو بقية Shards عندها موارد متاحة.

دي مشكلة Hotspot.

#### Why is it a problem?

لأن عددًا كبيرًا من Requests بيتركز على جزء واحد من النظام.

وبالتالي، زيادة عدد Shards مش بالضرورة تحل المشكلة لو كل الطلبات ما زالت متجهة إلى نفس Shard.

### 14.8 JOIN Across Shards

في قاعدة بيانات واحدة، تنفيذ JOIN بين جدولين قد يكون مباشرًا نسبيًا.

لكن لو البيانات موزعة على Shards مختلفة، ممكن نحتاج إلى تنفيذ عمليات عبر أكثر من Database Server.

ده بيزيد التعقيد، وممكن يتطلب نقل بيانات بين الخوادم أو تنسيق نتائج الاستعلامات.

### 14.9 Denormalization

الـ Denormalization هي تنظيم البيانات بطريقة قد تتضمن تكرار بعض البيانات لتقليل تكلفة الاستعلامات.

الشابتر بيذكرها كإحدى الطرق اللي قد تساعد على تقليل الحاجة إلى JOIN بين Shards.

مثلًا، بدلًا من الاعتماد على جداول موزعة لجلب كل تفاصيل Order، ممكن يحتفظ النظام ببعض بيانات العميل داخل سجل الطلب نفسه.

لكن ده له ثمن:

- تكرار البيانات.
- زيادة مساحة التخزين.
- الحاجة إلى تحديث النسخ المتكررة بصورة صحيحة.
- احتمال اختلاف البيانات إذا لم تتم المزامنة كما ينبغي.

لذلك، Denormalization مش حلًا مجانيًا؛ هي مقايضة بين تكلفة الاستعلام وتعقيد تحديث البيانات.

## 15. Replication vs. Sharding

من المهم جدًا التمييز بين المصطلحين دول.

### Replication

الـ Replication معناها إنشاء نسخ إضافية من البيانات.

النسخ تحتوي على البيانات نفسها، أو على نسخة منها قد تتأخر عن المصدر حسب آلية المزامنة.

الأهداف المحتملة:

- توزيع عمليات القراءة.
- تحسين التوافر.
- توفير نسخ إضافية من البيانات.

### Sharding

الـ Sharding معناها تقسيم البيانات إلى أجزاء مختلفة.
كل Shard تحتوي على جزء من البيانات بدلًا من تكرار كل البيانات على كل Shard.

الأهداف المحتملة:

- توزيع حجم البيانات.
- توزيع عمليات الوصول.
- تجاوز حدود Server واحدة عند الحاجة.

### Comparison

| المقارنة           | Replication                      | Sharding                          |
| ------------------ | -------------------------------- | --------------------------------- |
| الفكرة             | نسخ البيانات                     | تقسيم البيانات                    |
| محتوى الخوادم      | نسخ من نفس البيانات              | أجزاء مختلفة من البيانات          |
| الهدف              | توزيع القراءة وتحسين التوافر     | توزيع الحجم والحمل                |
| التحدي             | مزامنة النسخ والتعامل مع التأخير | توزيع البيانات وتوجيه الاستعلامات |
| يمكن الجمع بينهما؟ | نعم                              | نعم                               |

ممكن نظام كبير يستخدم Sharding لتقسيم البيانات، ويستخدم Replication لكل Shard لتوفير نسخ إضافية.

## 16. Important Terminology

| المصطلح            | المعنى                                                       |
| ------------------ | ------------------------------------------------------------ |
| Scalability        | قدرة النظام على التعامل مع زيادة الحمل                       |
| Bottleneck         | المكون الذي يحد من أداء النظام                               |
| Web Tier           | الطبقة المسؤولة عن التعامل مع الطلبات ومنطق التطبيق          |
| Data Tier          | الطبقة المسؤولة عن تخزين البيانات وإدارتها                   |
| Vertical Scaling   | زيادة موارد الجهاز الحالي                                    |
| Horizontal Scaling | إضافة أجهزة أو Servers                                       |
| Load Balancer      | توزيع الطلبات على مجموعة Servers                             |
| Health Check       | فحص حالة Server أو Component                                 |
| Replication        | الاحتفاظ بنسخ إضافية من البيانات                             |
| Replication Lag    | تأخر وصول التحديثات إلى Replica                              |
| Cache              | تخزين مؤقت للبيانات أو النتائج                               |
| Cache Hit          | البيانات المطلوبة موجودة في Cache                            |
| Cache Miss         | البيانات غير موجودة أو غير صالحة في Cache                    |
| TTL                | مدة صلاحية العنصر المخزن مؤقتًا                              |
| Eviction           | إزالة عناصر من Cache لإفساح مساحة                            |
| CDN                | شبكة موزعة جغرافيًا لتقديم المحتوى                           |
| Stateful           | يعتمد على الاحتفاظ بحالة محلية بين الطلبات                   |
| Stateless          | لا يعتمد على حالة محلية للمستخدم بين الطلبات                 |
| Shared Store       | مخزن مشترك تستطيع عدة Servers الوصول إليه                    |
| Data Center        | بنية تحتية لتشغيل الأنظمة                                    |
| GeoDNS             | توجيه DNS قد يعتمد على الموقع الجغرافي                       |
| Message Queue      | وسيط للرسائل والمهام                                         |
| Producer           | المكون الذي يرسل الرسائل                                     |
| Consumer           | المكون الذي يعالج الرسائل                                    |
| Logging            | تسجيل الأحداث                                                |
| Metrics            | قياسات رقمية لأداء النظام                                    |
| Automation         | تنفيذ المهام المتكررة بصورة آلية                             |
| CI                 | التحقق الآلي من تغييرات الكود                                |
| Sharding           | تقسيم البيانات إلى أجزاء موزعة                               |
| Sharding Key       | المفتاح المستخدم لتحديد مكان البيانات                        |
| Resharding         | إعادة توزيع البيانات بين Shards                              |
| Hotspot            | تركز الحمل على جزء محدد من النظام                            |
| Denormalization    | تكرار بعض البيانات أو إعادة تنظيمها لتقليل تكلفة الاستعلامات |
| SPOF               | مكون وحيد قد يؤدي تعطله إلى توقف النظام أو وظيفة مهمة        |
