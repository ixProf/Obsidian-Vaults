# يعني إيه Data-Intensive Application؟

التطبيقات الحديثة غالبًا بتكون **Data-Intensive** مش **Compute-Intensive**.

يعني المشكلة الأساسية مش قوة المعالج (CPU)، لكن بتكون في:

- التعامل مع كميات ضخمة من البيانات.
- إدارة بيانات معقدة.
- التعامل مع بيانات بتتغير بسرعة كبيرة.


بمعنى آخر: **البيانات نفسها هي التحدي الحقيقي**.

---

# المكونات الأساسية لأي Data-Intensive Application

معظم التطبيقات بتعتمد على مكونات جاهزة بدل ما تبني كل حاجة من الصفر.

| المكوّن                           | وظيفته                                                    |
| --------------------------------- | --------------------------------------------------------- |
| Database                          | تخزين البيانات واسترجاعها                                 |
| Cache                             | تخزين النتائج المتكررة لتسريع القراءة                     |
| Search Index                      | البحث بالكلمات والفلاتر                                   |
| Message Queue / Stream Processing | إرسال البيانات بين الخدمات بشكل غير متزامن (Asynchronous) |
| Batch Processing                  | معالجة كميات كبيرة من البيانات على فترات                  |

---

# ليه ما بنبنيش الأنظمة دي بنفسنا؟

لأن الأنظمة دي موجودة بالفعل ومجرّبة.

أمثلة:

- بدل ما تكتب Storage Engine بنفسك ==استخدم Database جاهزة.==
- بدل ما تعمل Cache System من الصفر ==استخدم Redis.==


مع الوقت الأدوات دي بقت قوية جدًا لدرجة إن المطورين بيستخدموها من غير ما يفكروا كتير في طريقة عملها الداخلية.

---

# التحدي الحقيقي: اختيار الأداة المناسبة

مش كل قواعد البيانات أو أنظمة التخزين شبه بعض.

كل تطبيق ليه احتياجات مختلفة مثل:

- السرعة (Speed)
- قابلية التوسع (Scalability)
- الاعتمادية (Reliability)
- إمكانيات البحث (Search)
- الاتساق (Consistency)

علشان كده

- فيه أنواع كتير من Databases.
- فيه أنواع كتير من Caches.
- فيه أنواع كتير من Search Engines.


واختيار المجموعة المناسبة مش دايمًا سهل.

---

# ليه الكتاب بيستخدم مصطلح Data Systems؟

زمان كنا بنفصل بين:

- Databases
- Caches
- Queues
    

لكن الأنظمة الحديثة بدأت تدمج الوظائف دي مع بعض.

## مثال: Redis

Redis ممكن يشتغل كـ:

- Database
- Cache
- Message Queue
    

في نفس الوقت.

---

## مثال: Kafka

Kafka يعتبر:

- Message Queue
- Durable Storage System
    

في نفس الوقت.

---

عشان كده مصطلح <mark style="background: #FFF3A3A6;">**Data System** أشمل من كلمة Database.</mark>

---

# أداة واحدة مش كفاية

في الأنظمة الكبيرة غالبًا أداة واحدة مش هتحقق كل المتطلبات.

الحل:

1. نقسم النظام لمهام صغيرة.
2. نستخدم <mark style="background: #FFF3A3A6;">أفضل</mark> أداة لكل مهمة.
3. نوصل الأدوات ببعض عن طريق Application Code.
    

مثال:

```text
User
  ↓
Application
  ↓
Database
  ↓
Cache
  ↓
Search Index
```

كل مكوّن متخصص في شغل معين.

---

# مشكلة التزامن بين الأنظمة (Synchronization)

لو عندك:

```text
Database
Cache
Search Index
```

يبقى لازم كلهم <mark style="background: #FFB86CA6;">يكونوا متزامنين</mark>.

مثال:

### Database

هي المصدر الأساسي للحقيقة (Source of Truth).

### Cache

بتخزن البيانات المطلوبة بكثرة.

### Search Index

بتخزن نسخة مناسبة للبحث.

لو التزامن فشل:

- المستخدم يشوف بيانات قديمة.
- نتائج البحث تبقى غلط.
- يحصل عدم اتساق في النظام.

```text

```

لازم تضمن:

- صحة البيانات.
- تحديث الـ Cache.
- صحة نتائج البحث.
- عدم فقدان البيانات.

# أهم الأسئلة في تصميم Data Systems

## 1. Reliability (الاعتمادية)

أسئلة مثل:

- إزاي البيانات تفضل صحيحة؟
- إيه اللي يحصل لو سيرفر وقع؟
- إزاي نمنع فقدان البيانات؟
    

---

## 2. Scalability (قابلية التوسع)

هل النظام يقدر يتعامل مع:

- مستخدمين أكتر؟
- Requests أكتر؟
- بيانات أكتر؟


---

## 3. Performance (الأداء)

هل:

- زمن الاستجابة يفضل سريع؟
- النظام يتحمل الضغط؟
    

---

## 4. API Design

- العميل هيستخدم إيه؟
- إزاي نخفي التعقيد الداخلي؟

# Reliability (الاعتمادية)

## يعني إيه Reliability؟

النظام يعتبر Reliable لما <mark style="background: #FFF3A3A6;">يفضل شغال بشكل صحيح حتى لو حصلت مشاكل</mark>.

المستخدم متوقع:

- البرنامج يعمل كما هو مطلوب.
- يتعامل مع أخطاء المستخدم.
- يحافظ على أداء مقبول.
- يمنع الوصول غير المصرح به.
    

---

### التعريف المهم

> Reliability = <mark style="background: #FFF3A3A6;"> قدرة النظام على الاستمرار في العمل بشكل صحيح حتى عند حدوث مشاكل</mark>.

---

# Fault vs Failure

## Fault

مشكلة في ==مكوّن واحد فقط==.
أمثلة:

- هارد ديسك تلف.
- سيرفر فصل.
- Bug في كود معين.

---

## Failure

فشل <mark style="background-color: #FFF3A3A6;">النظام بالكامل</mark> في تقديم الخدمة.

مثال:

```text
Disk Crash
    ↓
Fault

Website Down
    ↓
Failure
```

---

## الهدف الأساسي

```text
Faults should NOT become Failures
```

يعني:

> أي مشكلة ==محلية ما تتحولش لفشل كامل للنظام==.

وده اسمه:

### Fault Tolerance

---

# Fault-Tolerant Systems

النظام بيتصمم بحيث يتوقع حدوث أخطاء ويستمر في العمل.

لكن:

==لا يوجد نظام يستطيع تحمل كل الأخطاء الممكنة.==

مثال:

```text
كل السيرفرات اتحرقت في حريق
```

مفيش نظام طبيعي يقدر يتعامل مع ده.

لذلك بنركز على الأخطاء المتوقعة.

---

# اختبار الاعتمادية عن ==طريق إحداث أخطاء عمدًا==

المهندسين أحيانًا بيكسروا النظام بنفسهم!
ليه؟

عشان يختبروا قدرة النظام على التعافي.

أمثلة:

- إيقاف سيرفرات عشوائيًا.
- قتل Processes فجأة.
    

---
## مثال مشهور

شركة Netflix طورت أداة اسمها:

Chaos Monkey

وظيفتها:

إيقاف ==سيرفرات عشوائية أثناء التشغيل الحقيقي للتأكد من قدرة النظام على التعافي.==
# أنواع Faults

ثلاثة أنواع رئيسية:

1. Hardware Faults
2. Software Faults
3. Human Errors
    

---

# أولًا: Hardware Faults

أعطال مادية في البنية التحتية.

أمثلة:

- Hard Disk Crash
- RAM Failure
- Power Outage
- Network Cable Failure
- Server Failure
    

---

## ليه الأعطال دي متوقعة؟

متوسط عمر الهارد:

```text
10 - 50 سنة
```

يبدو رقم كبير.

لكن لو عندك:

```text
10000 Hard Disks
```

فغالبًا هيتلف:

```text
حوالي هارد واحد كل يوم
```

لذلك:

> فشل ==الهاردوير شيء طبيعي وليس استثناء.==

---

# الحل التقليدي: Redundancy

يعني وجود نسخة احتياطية.

## في التخزين

```text
RAID
```

لو ==هارد وقع==، هارد آخر يكمل الشغل.

## في السيرفرات

```text
Dual Power Supply
```

مزود طاقة احتياطي.

## في مراكز البيانات

```text
Batteries + Diesel Generators
```

وقت انقطاع الكهرباء.

---

# الاتجاه الحديث: Software Fault Tolerance

بدل الاعتماد فقط على الهاردوير.

الفكرة:

```text
Machines WILL Fail
```

الأجهزة هتتعطل أكيد.

فبنصمم السوفت وير بحيث يتعامل مع ده.
## مثال

بدل:

```text
Server واحد قوي
```

نستخدم:

```text
100 Servers
```

لو واحد وقع:

```text
99 يكملوا الشغل
```

وما يسمى بال Load Balancer

# Rolling Upgrade

ميزة إضافية.

بدل ما توقف النظام كله للتحديث:

```text
Update Server 1
Update Server 2
Update Server 3
...
```

الخدمة تفضل شغالة أثناء التحديث.

---

# ثانيًا: Software Faults

==أخطر من أعطال الهاردوير==.

لأن ==Bug واحد ممكن يضرب كل السيرفرات== في نفس اللحظة.

## أمثلة

### Software Bug

Input معين يوقع كل السيرفرات.

---

### Resource Exhaustion

برنامج يستهلك:

- CPU بالكامل
- RAM بالكامل
- Disk بالكامل
- Network بالكامل
    

==فتفشل الخدمات الأخرى==.

---
### Dependency Failure

==خدمتك تعتمد على خدمة== أخرى.

الخدمة الأخرى:

- بطيئة.
- واقفة.
- ترجع بيانات خاطئة.
    

فتأثر عليك.

---

### Cascading Failure

من أشهر المفاهيم.

مشكلة صغيرة ==تؤدي لمشكلة أكبر ثم أكبر==.

مثال:

```text
Database Slow
      ↓
Application Waiting
      ↓
Threads Exhausted
      ↓
Requests Timeout
      ↓
Service Down
```

---

# ليه Software Bugs صعبة؟

لأنها قد تظل مخفية سنوات.

ولا تظهر إلا في ظروف نادرة جدًا.

غالبًا المبرمج يفترض:

```text
This will never happen
```

ثم يحدث فعلًا.

---
# تقليل Software Faults

### Careful Design
تصميم جيد من البداية.
### Thorough Testing

اختبار الحالات العادية والاستثنائية.
### Isolation
عزل المكونات عن بعضها.
### Crash & Restart
إعادة تشغيل الخدمات المعطلة تلقائيًا.
### Monitoring
مراقبة مستمرة للنظام.
### Self-Checking
مثال:

```text
Incoming Messages = Outgoing Messages
```

لو مش متساويين:

```text
Raise Alert
```

## Better Design
تصميم واجهات تمنع الخطأ قدر الإمكان.

==بيئة تجريبية منفصلة== عن النظام الحقيقي.

## Testing

- Unit Testing
- Integration Testing
- System Testing
- Manual Testing

## Easy Recovery

سهولة التراجع عن الأخطاء.

أمثلة:

- Rollback Configuration

مراقبة:

- Error Rates
- Performance
- Resource Usage

للحصول على:

- تشخيص أسرع.
- حل أسرع للمشاكل.

تدريب العاملين يقلل الأخطاء البشرية.
