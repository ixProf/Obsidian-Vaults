اتكلمنا عليها قبل كدا وهي عملية اني انقل الحاجة من ال Working Directory لل index

في الاول لما اعمل فايل جديد او يكون في فايل جديد ف الفايل دا بيكون في الWorking Directory ساعتها هيكون Untracked فعلشان اخلي git يتعرف عليه ف انا هعمله Track عن طريق اني احطه في ال Index ف عندي git add بتعمل الشغل دا 
تقدر تستخدمها ف اكتر من حاجه مثلا:
- لو `git add filename` كدا انت هتضيف فايل معين باسمه

## Ignoring Files

لو عايز تتجاهل فايلات معينة ومترفعهاش فهتستخدم gitignore يطلع اي دا ؟
- عبارة عن ملف كدا `gitignore.` لو عندك حاجه انت مش حابب تضيفها عندك في الريبو على جيت ف انت المكان دا هتحط فيه كل حاجه انت مش عايزها ولما تعمل git add . مش هيضيفها معاهم 
```bash
git add --dry-run -A 
```
فهو هنا هيضيفلك الgitignore 

دا فحالة ان الحاجه دي مش عايزها تترفع اصلا على الريبو او تتشارك مع الناس

اما بقى لو عندك حاجه هي خاصة بيك انت ومش عايز مثلا حد يشوفها مثلا البروسيس بتاعتك وانت بتشتغل ف انت بتحطها فمكان اسمه
```txt
.git/info/exclude
```

هنا انت هتقدر تسيفه عادي على الريبو وتبقى متجاهل التعديلات بتاعتها ولكن هتبقى خاصة ليك انت بس بدون ما تشاركها مع حد

يبقى الفرق كدا فين؟


| ignoring command  | meaning                                                                                                                 |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------- |
| .gitignore        | used to track what 'we' ignore (as a team)                                                                              |
| .git/info/exclude | used when the ignored files are auxiliary files that live inside the repository but are specific to one user's workflow |

> اي حاجه اتعملها Staging لو جيت تحطها في gitignore فمش هيتعمله ignore خلاص

ولو عايز تحطها في ال ignore ف انت هتشيله من ال staging عن طريق
```bash
git rm --cached <filename>
```

فـ ساعتها هيكون Untracked فتقدر ساعتها أنك تحطه في ال gitignore

## Rollback Strategies

هنا في الاول بيقولك لو انت عايز تشيل حاجه من ال Staging Area الي هي يعني من الاخر عملية الـUnstaging دلوقتي افتراضا انت عملت كوميت على تعديل بالغلط وحاجه يعني انت مش عايز تعملها وعايز ترجع لكوميت معين، ف انت عندك 3 استراتيجيات وهما:
- الـrevert
- الـreset
- الamend

### 2: الـReset

هنا فكرة الReset هو كأنه بيعمل reset للRefernces بتاعتي و الindex وكل حاجه يعني كأنك معملتش ال commit دي اصلا وليها درجات:
- ال `soft--`: التعديلات الي انت لسه حاططها في ال index هتفضل عندك وهشيلك اخر حاجه (كأنك لسه معملتش commit)
- ال `mixed--`: التعديلات الي انت حاططها في الindex واخر حاجه هشيلهالك (لو عايز ارجع كأني لسه مضفتش الحاجه دي فال index)
- ال `hard--`: كل حاجه هشيلهالك كأن مفيش حاجه (كأنك معدلتش اي حاجه)

## أولًا: يعني إيه HEAD أصلًا؟

في Git عندك 3 حاجات مهمين:

```text
Working Directory
Staging Area
HEAD
```

الـ `HEAD` هو ببساطة:

> **مؤشر بيحدد أنت واقف حاليًا عند أنهي Commit.**

لكن الـ `HEAD` مش دايمًا بيشير للـ Commit بشكل مباشر.

وده اللي بيفرق بين:

- Attached HEAD
    
- Detached HEAD
    

---

## 1. Attached HEAD

ده الوضع الطبيعي.

افترض عندك التاريخ ده:

```text
A <- B <- C
          ^
        master
```

والـ `HEAD` على `master`:

```text
HEAD -> master -> C
```

هنا بنقول:

> الـ HEAD **Attached** بالـ `master`.

يعني الـ HEAD لا يشير مباشرة إلى `C`.

هو يشير إلى:

```text
HEAD -> master -> C
```

---

### طب لما تعمل Commit؟

أنت حاليًا:

```text
HEAD -> master -> C
```

عملت:

```bash
git commit -m "D"
```

Git يعمل:

```text
HEAD -> master -> D -> C -> B -> A
```

لاحظ حاجة مهمة جدًا:

**الـ HEAD نفسه مش هو اللي بيتحرك مباشرة.**

اللي حصل إن:

```text
master: C -> D
```

والـ HEAD لسه بيقول:

```text
HEAD -> master
```

وبالتالي تلقائيًا بقى شايف `D`.

---

### ليه بنقول Attached؟

لأن الـ HEAD **مربوط بالـ Branch**.

يعني:

```text
HEAD -> master -> D
```

فالـ Branch هو اللي بيحدد الـ Commit اللي أنت واقف عليه.

---

## 2. Detached HEAD

دلوقتي افترض إن عندك:

```text
A <- B <- C <- D
              ^
            master
```

وعايز تروح للـ Commit `B`.

تعمل:

```bash
git checkout B
```

دلوقتي الوضع بقى:

```text
HEAD -> B

master -> D
```

يعني الـ HEAD **مش بيشير للـ master**.

هو بيشير مباشرة إلى `B`.

بدل:

```text
HEAD -> master -> D
```

بقى:

```text
HEAD -> B
```

وده اسمه:

> **Detached HEAD**

---

### طيب إيه المشكلة؟

مفيش مشكلة في حد ذاته.

أنت تقدر تعمل حاجات عادي جدًا:

```bash
git log
git show
git diff
git test
```

وتقدر حتى تعدل الكود وتعمل Commit.

مثلاً:

```text
master -> D

A <- B <- C
      \
       Experimental <- HEAD
```

عملت:

```bash
git commit -m "Experimental"
```

هيبقى:

```text
master -> D

A <- B <- C <- Experimental <- HEAD
```

لاحظ:

**master لم يتحرك.**

ليه؟

لأن الـ HEAD كان Detached، وبالتالي مفيش Branch مربوط بالـ HEAD علشان يتحرك مع الـ commit.

---

### هنا الخطر الحقيقي

لو خرجت من الـ Detached HEAD:

```bash
git switch master
```

هيبقى:

```text
master -> D

A <- B <- C <- Experimental
```

الـ `Experimental` لسه موجود في Git لفترة، لكن **مفيش Branch بيشاور عليه**.

يعني أصبح:

> Unreferenced commit

وممكن Git في المستقبل يعتبره unreachable ويشيله أثناء Garbage Collection.

---

### عشان كده لو عجبك الـ Commit

وأنت في Detached HEAD وعملت:

```text
Experimental <- HEAD
```

اعمل:

```bash
git switch -c experiment
```

دلوقتي:

```text
experiment -> Experimental <- HEAD
```

وبكده حفظت الـ commit في Branch.

---

## احفظ الجملة دي

> الـ**Attached HEAD:** أنا واقف على Branch، والـ Branch هو اللي بيشاور على الـ Commit بتاعي.

> الـ**Detached HEAD:** أنا واقف على Commit مباشرة، ومفيش Branch ماسك الـ HEAD.

وده سبب إن **Detached HEAD مفيد جدًا لما تكون عايز تستكشف أو تجرب حالة قديمة من المشروع بدون ما تحرك أي Branch**.

## الفرق بين `checkout` و `reset`

ببساطة جدًا:

### `checkout`

بيغير **أنت واقف فين**.

مثلاً:

```text
A <- B <- C <- D
          ^
        master
```

عملت:

```bash
git checkout B
```

يبقى:

```text
HEAD -> B

master -> D
```

يعني **الـ Branch متحركش**، أنت بس رحت لـ `B`.

---

### `reset`

بيغير **الـ Branch واقف فين**.

مثلاً:

```text
A <- B <- C <- D
              ^
            master
```

عملت:

```bash
git reset B
```

يبقى:

```text
HEAD -> master -> B
```
يعني **الـ master نفسه رجع لـ B**.
