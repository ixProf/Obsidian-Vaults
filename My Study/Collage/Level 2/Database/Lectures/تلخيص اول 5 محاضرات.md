#### **1. Data Models**

- A **data model** defines the structure of a database, ==including data types, relationships, and constraints.==
- It determines ==how data is connected, processed, and stored==.
نموذج البيانات هو الطريقة اللي بنوصف بيها هيكلة قاعدة البيانات، وده بيشمل أنواع البيانات، العلاقات بينها، والقيود اللي بتتحط عليها. بمعنى تاني، النموذج ده هو اللي بيحدد إزاي البيانات مترابطة، وبتتخزن، وبتتعالج جوه النظام.

#### **2. Categories of Data Models**

- **Conceptual ==(High-level, Semantic)== Data Models:** Represent data in a way that users understand (e.g., entity-based or object-based models).
دي بتمثل البيانات بطريقة قريبة من طريقة تفكير المستخدمين العاديين. =="علشان كدا اسمها High-Level"==
بتُعرف كمان باسم ==النماذج الكيانية أو المعتمدة على الكائنات== (Entity-based or Object-based Models).


- **Physical (Low-level, Internal) Data Models:**
	- Describe ==how data is stored== at the hardware level.
	- Usually detailed in DBMS design and administration manuals.
بتركز على التفاصيل اللي بتوصف إزاي البيانات بتتخزن جوه الكمبيوتر من الناحية التقنية.
المعلومات دي بتكون موضحة بشكل مفصل في أدلة تصميم وإدارة أنظمة قواعد البيانات.

- **Implementation (Logical/Representational) Data Models:** Used in commercial databases, such as the relational model.
مزيج بين الاتنين 
و دي اللي بتُستخدم في معظم أنظمة إدارة قواعد البيانات التجارية، زي النموذج العلائقي (Relational Model).

#### **3. Database Schema and Database State**

- **Database Schema:** The structure of a database, including data types and constraints.
هو الوصف العام لهيكل قاعدة البيانات، وبيشمل أنواع البيانات، العلاقات، والقيود.
- **Schema Diagram:** A visual representation of the schema.
التمثيل البصري للإسكيما
- **Database State:** Represents the database content at a specific moment in time.
بتعبر عن المحتوى الفعلي لقاعدة البيانات في لحظة معينة.
- **Initial Database State:** The state when the database is first loaded.
هي الحالة اللي بتكون عليها قاعدة البيانات أول ما يتم تحميل البيانات فيها لأول مرة.
- **Difference:** The schema is mostly static, while the database state changes with updates.
- الاسكيما ثابتة ونادرًا ما بتتغير.
- حالة البيانات بتتغير كل مرة بيتم فيها تحديث البيانات أو إضافة سجلات جديدة.
- الاسكيما يُعرف بـ **الـ Intension**، وحالة البيانات تُعرف بـ **الـ Extension**.

# **(ERD)**

## **🔹 Introduction to ERD**

- An **Entity-Relationship Diagram (ERD)** is a ==**graphical representation**== of a database structure. 📊
- It **defines entities, their attributes, and relationships** between them.
- ERDs help in the **conceptual design** of databases before implementation in a relational model. 🏗️
- The primary components of an ERD are:
    - **Entities** (represented as ==rectangles==) 🟥
    - **Attributes** (represented as ==ovals==) 🟠
    - **Relationships** (represented as ==diamonds==) ♦️
    - **Cardinalities** (depicted with lines and symbols) 🔀

---

## **🔹 Types of Keys in Databases**

### **1️⃣ Primary Key (PK) 🔑**

- A unique identifier for each record in a table.
- **Cannot ==contain duplicate values== or NULL values.**
- Example:
    - In a **Student** table, `Student_ID` is a primary key because each student has a unique ID.

### **2️⃣ Foreign Key (FK) 🔗**

- A field in one table that ==**references** the primary key in another table.==
- Used to **establish relationships between tables**.
- Example:
    - In an **Enrollment** table, `Student_ID` is a **foreign key** that links to the `Student_ID` in the **Student** table.

### **3️⃣ Candidate Key 🎯**

- Any column that could be used as a **primary key**.
- A table may have ==multiple candidate keys==, but only one is chosen as the **primary key**.
- Example:
    - In an **Employee** table, `Emp_ID`, `Email`, and `Phone` could all be **candidate keys**.

### **4️⃣ Composite Key 🏗️**

- A key composed of **multiple attributes** that uniquely identify a record.
- Example:
    - In a **Work_Hours** table, a combination of `(Emp_ID, Proj_ID)` serves as a **composite key** since an employee can work on multiple projects.

### **5️⃣ Super Key 💡**

- A **set of attributes** that uniquely identify a row.
- Any **super key** containing unnecessary attributes is **not minimal** (hence, not a primary key).

---

## **🔹 Types of Relationships in ERD**

### **1️⃣ Binary Relationship ⚡**

- A relationship ==between **two entities**==, such as **Student - Course**.
- Represented by a **diamond** connecting the two entities.

### **2️⃣ N-ary Relationship 🔄**

- A relationship involving ==**more than two entities**==.
- Example: **(Employee - Project - Department)**

### **3️⃣ Unary ( Recursive ) Relationship 🔁**

- A relationship where an entity **relates to itself**.
- Example:
    - **"Employee supervises another Employee"** (One employee is the supervisor, another is the subordinate).
---

## 📘 Relationship Cardinality

**Relationship cardinality** defines how **many times an entity from one entity set can be associated** with entities from another set through a relationship.

It's crucial in **Entity-Relationship (ER) modeling** in database design.

---

## 🧩 Types of Cardinality:

### 1️⃣ **One-to-One (1:1)**

Each entity in **Entity Set A** is related to **only one** entity in **Entity Set B**, and vice versa.

#### Example:

- A **Person** has **one National ID**, and each National ID belongs to only one person.
    

```
Person (1) ←→ (1) NationalID
```

---

### 2️⃣ **One-to-Many (1:N)**

An entity in **Set A** can be related to **many entities** in **Set B**,  
but each entity in **Set B** is related to **only one** entity in **Set A**.

#### Example:

- A **Manager** supervises **many Employees**,  
    but each **Employee** has only **one Manager**.
    

```
Manager (1) ←→ (N) Employee
```

---

### 3️⃣ **Many-to-One (N:1)**

Each entity in **Set A** is related to **one entity** in **Set B**,  
but each entity in **Set B** can be related to **many entities** in **Set A**.

#### Example:

- An **Employee** belongs to **one Department**,  
    but a **Department** has **many Employees**.
    

```
Employee (N) ←→ (1) Department
```

---

### 4️⃣ **Many-to-Many (M:N)**

Entities in **both sets** can be associated with **many entities** in the other.

#### Example:

- A **Student** can enroll in **many Courses**,  
    and each **Course** can have **many Students**.
    

```
Student (M) ←→ (N) Course
```

---

## 💡 Notes:

- Cardinality plays a key role when converting an ER model to a **relational schema**.
    
- In **Many-to-Many** relationships, we usually need a **bridge table** (associative entity) to represent the relationship.
    

---

## 📝 Summary Table:

|Type|Example|Notation|
|---|---|---|
|One-to-One|Person ↔ NationalID|1 : 1|
|One-to-Many|Manager ↔ Employees|1 : N|
|Many-to-One|Employee ↔ Department|N : 1|
|Many-to-Many|Student ↔ Course|M : N|

---

## **🔹 Relationship Constraints**

1. **Total Participation (✅)**
    
    - Every entity in the set ==**must** participate== in the relationship.
    - Example: Every **employee** must belong to a **department**.
2. **Partial Participation (⚠️)**
    
    - Some entities ==**may or may not** participate== in the relationship.
    - Example: Some **students** may not be **enrolled** in any course.

# 🎯 **Enhanced Entity-Relationship Diagram (EER or EERD)**

---

## 🔹 **What is EER?**

📌 The **Enhanced Entity-Relationship (EER)** model is an extension of the traditional **Entity-Relationship (ER)** model. It introduces **advanced modeling concepts** to handle more complex data relationships.

### ✨ EER includes advanced features such as:

1. **Generalization & Specialization** (Inheritance)
    
2. **Superclasses & Subclasses**
    
3. **Disjoint and Overlapping Constraints**
    
4. **Aggregation and Categorization**
    

> 🔍 **EER** is used when modeling complex databases that require more flexibility and detail than a basic ERD can provide.

---

## 🔹 **ERD vs. EERD – Key Differences**

|**ERD (Entity-Relationship Diagram)**|**EERD (Enhanced Entity-Relationship Diagram)**|
|---|---|
|Uses basic entities and relationships.|Adds advanced concepts like inheritance and categorization.|
|Suitable for simple systems.|Designed for more complex and layered systems.|
|Does not support subclasses/superclasses.|Supports `Subclasses`, `Superclasses` via generalization/specialization.|
|Entities are treated independently.|Allows hierarchical relationships among entities.|

---

## 🔹 **Main Components of EER**

### 1️⃣ **Generalization & Specialization (Inheritance)**

These define hierarchical relationships between entities.

#### 🔸 Generalization

- Combines multiple **similar entities** into a more **general superclass**.
    
- **Bottom-Up Approach**
    

**Example:**

```text
          Person
         /      \
    Teacher   Student
```

#### 🔸 Specialization

- Divides a **general entity** into **more specific subclasses**.
    
- **Top-Down Approach**
    

**Example:**

```text
          Employee
         /       \
    Manager   Developer
```

---

### 2️⃣ **Disjoint vs. Overlapping Constraints**

When an entity is specialized into subclasses, we define how they relate:

- **Disjoint Constraint (exclusive):**  
    An entity **belongs to only one subclass**.  
    _e.g., An Employee can be either a Manager **or** a Developer, not both._
    
- **Overlapping Constraint (inclusive):**  
    An entity **can belong to multiple subclasses**.  
    _e.g., A Person can be both a Teacher and a Researcher._
    

---

### 3️⃣ **Aggregation**

📌 Used when a **relationship participates in another relationship**.

**Example:**

```text
Employee --- WorksOn --- Project
                  |
               Manages
                  |
              Department
```

- Here, the `WorksOn` relationship is treated as an **entity** so it can participate in the `Manages` relationship.
    
- This abstraction is called **aggregation**.
    

---

### 4️⃣ **Categorization**

📌 Used when **subclasses inherit from multiple different entity sets**.

**Example:**

- Suppose we have an `Account` entity, which could be either a `SavingsAccount` or a `CreditAccount`.
    
- A `Customer` can be linked to either type of account.
    

```text
       Account
       /     \
Savings     Credit
              \
             Customer
```

---

## 🔹 **Practical Examples of EERD**

### 🏥 **Hospital System**

#### Entities:

- **Person (Superclass)**
    
- Subclasses: `Doctor`, `Nurse`, `Patient`
    

#### Relationships:

- `Doctor` works in a `Department`
    
- `Patient` has a `MedicalRecord`
    

**EERD Structure:**

```text
          Person
         /   |   \
    Doctor  Nurse  Patient
        |             |
   Department    MedicalRecord
```
---

## 🔹 **When Should You Use EER Instead of ER?**

✅ Use **EER** when your database includes:

- Inheritance hierarchies (specialization/generalization)
    
- Relationships involving other relationships (aggregation)
    
- Complex categorizations or shared structures
    
- Systems requiring advanced data modeling

# Data Modeling Using the Relational Model**

---

## 📌 **1. What is the Relational Model?**

The **relational model** is a formal way of organizing data into **tables (relations)**.

Each **relation** consists of:

- **Attributes**: Columns (fields)
    
- **Tuples**: Rows (records)
    
- **Schema**: Structure of a relation (like a table blueprint)
    
- **Instance**: The actual content (rows) at a specific point in time
    
- **Domain**: Set of valid values for an attribute
    

---

## 📘 **2. Terminology Overview**

|Term|Description|
|---|---|
|**Relation**|A table with rows and columns|
|**Attribute**|A named column in the table|
|**Tuple**|A row of values (record)|
|**Schema**|Definition of table structure (e.g. `Student(SID, Name, Age)`)|
|**Instance**|Actual data in the table at a given time|
|**Domain**|Allowed values for an attribute (e.g., Age ∈ Integers)|

---

## 🔑 **3. Types of Keys in Relational Model**

|Key Type|Description|
|---|---|
|**Super Key**|A set of one or more attributes that uniquely identifies a tuple in a relation|
|**Candidate Key**|A minimal super key (i.e., no extra attributes)|
|**Primary Key**|The chosen candidate key to uniquely identify tuples; must be **unique** and **not null**|
|**Foreign Key**|An attribute that refers to the primary key in another relation, ensuring **referential integrity**|

---

## ⚠️ **4. Integrity Constraints**

These rules ensure correctness and consistency of data:

### ✅ **Domain Constraint**

- Each attribute must take values from a predefined domain (type).
    
    - Example: `Age` must be an integer between 0 and 120.
        

### ✅ **Entity Integrity**

- The primary key of a relation **cannot be NULL**.
    
    - Every tuple must be uniquely identifiable.
        

### ✅ **Referential Integrity**

- A foreign key in one table must either:
    
    - Match a primary key in the referenced table, or
        
    - Be NULL
        

---

## 🔁 **5. Mapping ER Model to Relational Schema**

|ER Element|Mapping in Relational Model|
|---|---|
|**Entity**|Becomes a relation (table)|
|**Weak Entity**|Becomes a table with its own partial key + foreign key to owning entity|
|**1:1 Relationship**|Add foreign key to either entity (prefer side with total participation)|
|**1:N Relationship**|Add foreign key to the N-side entity|
|**M:N Relationship**|Create a new relation with foreign keys from both entities + any attributes of the relationship|
|**Multivalued Attribute**|Create a new relation with a foreign key to the original entity and one column for the multivalued attribute|
|**Composite Attribute**|Break it down into individual attributes (flatten)|

---

## 🧠 **7. Key Points**

- Be able to define and identify:
    
    - **Super key**, **Candidate key**, **Primary key**, **Foreign key**
        
- Understand and explain:
    
    - **Entity integrity**, **Referential integrity**, and **Domain constraint**
        
- Practice converting:
    
    - **ER diagrams** into relational schemas
        
    - Especially for 1:1, 1:N, and M:N relationships
        
- Know how to handle:
    
    - **Weak entities**
        
    - **Multivalued and composite attributes**
        

---

## 📌 Summary Table of Relationships:

|Relationship Type|Implementation|
|---|---|
|1:1|Add foreign key to one table|
|1:N|Add foreign key to the "many" side|
|M:N|Create new relation (junction table)|
|Weak Entity|Add foreign key from identifying entity + partial key|
|Multivalued Attr.|Create new relation with foreign key|
|Composite Attr.|Decompose into individual fields|
