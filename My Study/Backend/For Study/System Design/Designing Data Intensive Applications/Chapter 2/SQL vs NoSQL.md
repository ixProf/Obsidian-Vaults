# The Data Model

 - ليه يعتبر الداتا مودل اهم جزء في السوفت وير عموما؟
	 - لأن اي ابلكيشن ما هو الا وسيلة للتعامل مع الداتا، تخزنها ازاي؟ اي احسن طريقة؟ وامتى تسترجعها في اسرع وقت وقت ما تحتاجها
- طب اي هو الداتا مودل؟
	- ما هي إلا طريقة لتمثيل الداتا بطريقة ابسط بتسهلك التعامل معاها.

على سبيل المثال، انت لو App Developer:

فنظرتك عن الداتا هتلاقيها ما هي إلا : ناس وطلبات وشركات وأكشنز مثلا ودي تعتبر عنك النظرة الأولية (Layer 0)
- طبيعي الابلكيشن مش هيفهم الي انت تقصده غير لما تحول الحاجات دي لطريقة يفهمها
	- ف انت هتحول دول كدا ل Data Structures و Objects ف بالشكل دا انت عملت للداتا بتاعتك حاجه اسمها (Modeling)
	- واكيد انت برضو محتاج تخزن الداتا ستراكشرز دي في صورة داتا مفهومة اكتر وتستخدمها في اكتر من طريقة
		- في حالة التخزين دا هيكون في NoSQL فهتخزنها على شكل
			- لـJSON
			- لـXML
		- اما لو في حالة لو كان SQL
			- فهتبقى: Tables
		- وممكن تخزنها كمان على شكل Graph
	- بعد كدا الداتا بيز هيحولك الداتا دي لحاجتين:
		- يا إما Bytes تتحط في الرام
		- او يا إما Files تتخزن في الديسك
	- مهندسين الهارد وير ممكن يمثلوا البايتس دي على شكل
		- شحنات كهربائية
		- مجال مغناطيسي
		- ومضات ضوء

فالي احنا عملناه دا يسمى بال Data Model Layering كل ما تنزل لاير بتعمل Deep dive

## SQL

بيخزن الداتا على شكل Relations عبارة عن Tables (Columns - Rows) حافظ على مكانته كأهم انواع الداتا مودلنج علشان هو مستخدم في ال Business Data Processing  وبيغطي كل احتياجتهم
وهو اساسا معمول لـ Transactional / Batch Processing عمليات الدفع والتحويل وكمان الباتش المسؤول عن التقراير والمستندات

### Transactional Processing

لو عندي امر او اكتر للداتا بيز ساعتها لو تم تنفيذ الاوامر دي او الامر دا في الداتا بيز هيتعمله ==Commit== 
لو متنفذش فبيتعمله ==rollback==  

لو انت اشتريت كتاب فالسيستم لازم يتأكد ان معاك فلوس تكفي سعر الكتاب دا
وبيتأكد ان انت اتخصم منك فلوس الكتاب والبوك ستور خد فلوسه

لو اي عملية من دول منفعتش فالعملية كلها تفشل ويحصل rollback

## NoSQL

هو عبارة عن تصحيح للمشاكل الي ظهرت في ال SQL، طب اي المشاكل الي ظهرت في ال SQL ؟

- بدء ظهور الBig Data وال Scaling بتاع ال Relational Database مبقاش ينفع مع ال Scale الكبير دا فكان بيتعمل
	
	- تكبير للماشين الي انت شغال عليها (Vertical Scaling)
		
	- لكن مع الوقت الداتا بتكبر فبيكون من الصعب انها تتحط على ماشين واحدة فكان بيتعمل (Horizontal Scaling) فبيعمل sharpen للداتا
	
- ال SQL ليها Schema صارمة فـأنت ملزم تمشي على السكيما دي

	- ودا بيصعب عملية ال Migration للداتا، لو Table حجمة كبير فعملية ال Schema Build/Schema Change كانت بتاخد وقت كتير وفي بعض الاحيان بيخليك  تـLoad الـTable كله او تعمل block لل Write لحد ما تخلص Migration
		
	- وممكن الابلكيشن بتاعك يكون في داتا مش بتتبع نفس السكيما، فهتلاقي انك بتبني جدول كبير في اعمدة كتيرة معظمها فاضي لأن كل case بتبني اعمدة معينة والباقي مش تبعها
	
	- علشان كدا في الDocument Model هياخد منك الداتا منك من غير سكيما وانت بتكتبها، ف هو مش هيعمل Check من ناحية السكيما بس انت لازم تتأكد اذا كان الداتا موجودة ولا لا من ناحية الكود

- ف اتعمل مودل جديد مبني على فكره انه Distributed يعني متوزع في اكتر من سيرفر ويلغيلك حوار السكيما دا خالص

	- طب هنمثل العلاقة دي ازاي فال Relational DB ؟
		- الطريقة الاولى Normalization
			-  هنفصل كل نوع فيهم في جدول منفصل زي ما موجود فالرسمة ونربطهم ب foreign Key

			- يعني اي Normalize ؟

					- زي كل داتا مرتبطة ببعض تكون في جدول واحد 
					- يكون ليه Primary Key
					- الداتا ميكنش فيها تكرار مش موجود فأكتر من مكان
		
		- الطريقة التانية اني احط الداتا بتاعت التيبولز دي في عمود ك JSON/XML لكن دا اقل كفاءة من النورماليز
		- الطريقة التالتة اني اعملها Encoded واخليها text ساعتها مش هعرف اعمل عليها سيرش
	- طب هنمثلها ازاي مثلا في ال NoSQL ؟
		- افضل خيار في الحالة دي هنمثلها على شكل JSON وهنستخدم MongoDB ولو بصينا على الشكل دا
		![[Pasted image 20260623111122.png]]
		- هتلاقيها اسهل واحسن بكتير من الجداول
		- وكمان من ناحية البيرفورمنس فهي احسن برضو لأن ال Locality في ال JSON Doc احسن بكتير
			- يعني ايه Locality ؟
				- يعني الداتا الي محتاجها تكون قريبة مني في نفس المكان ومش هبذل مجهود اني اجمعها معايا سواء اني اقراها من جدول تاني او اعمل join 
		- طب لو في حالة ال Many-To-Many هتعمل اي؟ 
			- فحالة ال region

				- ولو احتجت تعدل الاسم هتحتاج تعمل ابديت لكل الدوكيومنت
					
				- ولما تعمل سيرش بال region_Id هيكون ادق من انك تعمل سيرش بال text
				
			- طبعا فكرت انك انت تستعمل ال region id وتعمل join بس ال join فال NoSQL ضعيف حبتين وان دي حاجه خاصة بشكل اكبر لل SQL

- هل ال Document Database بتعيد التاريخ؟
	
	- كان في مودلز مش عاجبها ال SQL بس لم يصمدوا امام العملاق SQL بسبب الكفاءة الي كان بيقدمها في انه يعمل joins بكل سهولة
		
	- واحد من المودلز دي هو  ال Hierarchical 
		- حاجه شبيهة بال JSON Model بانه يحط الداتا كلها في دوكيومنت واحده كأنها Tree of Nested Records زي الشكل دا:
		![[Pasted image 20260623115611.png]]
		- وكان كويس جدا مع 1-1 / 1-M وسيئ مع M-M علشان الجوينز طبعا
		
	- تاني مودل وهو ال Network Model
		- وهو شبيه جدا بال hierarchical لكنه اشبه بال Graph 
			
		- الـdocument كان ليها اكتر من parent وال links ما بين ال docs مكنتش foreign keys كانت حاجه اشبه بال pointers مكنتش تتحط في الميموري كانت تتحط في الديسك عادي لانها عبارة عن داتا محتاجة تتحفظ كان اسمها ==Access Path==  ولو عايز اوصل لحاجه همشي من الهيد وهفضل ادور عبر ال Access Paths لحد ما الاقي الداتا ولازم اتاكد بقى اني مكنش اخدت الداتا مرتين
			
		- طبعا دا سبب مشكلة فالداتا بيز انجن بقى بدل ما الحاجة تتعمل لنفسها لا انا اديت للمبرمج مسؤولية انه يراجع ورايا فطبعا انا ايه الي يخليني اروح لشئ يتعبني 
		![[Pasted image 20260623120946.png]]

- فعلشان كدا الناس اتجنبته واتجهت لل Relational Model علشان مكنش فيه التعقيد وكانت ال Relational Database فيها حاجه اسمها Query Optimizer ودا كان بيختار ال index المناسب الي يسترجع بيه الداتا وامتى يستخدمه 
- فبقى دورك كمبرمج انك تشوف عايز تAccess الداتا ازاي وهتعمل سيرش بأيه وتحط إندكس على العمود الي هتسرش عليه

- ال Document Model مهمة فحالة
	- لو الابب بتاعك مفيهوش علاقات many-to-many ساعتها هتبقى احسن واسرع من ال Relational Model
	- لو الابب بتاعك الداتا بتاعتك فيها Schema-less
